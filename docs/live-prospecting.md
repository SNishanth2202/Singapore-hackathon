# Live prospect discovery

The normal Lead Ranking page reads `/api/v1/prospecting`, never the synthetic ranking fixture or browser cache. A new installation has an empty list. Research discovers company names across industries from retrieved market headlines, validates citations and company identity, collects company-specific sources, and generates a grounded brief against the current editable seller catalogue. Known seller identities are excluded. Customer relationship is UNKNOWN; no simulated customer register, contact, commercial estimate, renewal deadline or engineering assessment enters this queue.

Discovery uses Google News RSS and attempts EDB's public announcement index. Individual research retrieves directory identity, background, current news and readable official company pages. An exact active GLEIF identity lookup is a fallback when directory matching is ambiguous or absent. Original dated discovery headlines remain attached to each immutable research snapshot. Headlines are labelled as headlines, not verified article bodies. Unsupported citations and service IDs are rejected; valid but unqualified candidates do not fill the top 15. The source coverage panel distinguishes automatic connectors, planned connectors, manual portals and optional configuration. This release does not claim all 35 sources from the supplied inventory are connected.

Settings define markets, a 15-minute to 30-day interval and a bounded 1–40 candidate budget, defaulting to three companies for new installations. There is no industry selector or required competition track. Legacy saved industry settings are accepted and discarded. Discovery combines broad business-event queries, digital-service queries and active catalogue signals, balancing items across feeds so the first feed does not consume the evidence budget.

Each job snapshots its settings and processes one candidate per worker step. Completed company dossiers appear immediately in Company research, including companies whose service fit is not yet supported. Validated opportunities also appear in the current top list before the batch finishes. Until the first current opportunity is ready, a previous successful list keeps its dates and is labelled as previous results. Duplicate workers are excluded by an atomic MongoDB lease with an ownership token and expiration; an interrupted step resumes from its saved cursor. A failed run retains the previous successful list with its timestamps. A genuine completed empty run clears old results. Run history is bounded to 20 summaries; full dossiers are excluded from history. Source research snapshots remain in the existing research store. Scheduling resumes from MongoDB after service restarts. Explicit local memory mode is temporary and does not prove disk/cloud durability.

If AI discovery is unavailable, a conservative headline-subject parser can retain names explicitly present in the retrieved sources. These are candidates, not qualified customers. An unresolved directory/registry identity may have a reported-name dossier, clearly labelled UNVERIFIED and excluded from ranking. Its original headlines are not relabelled or counted again as a registry profile. AI failures preserve retrieved sources without inventing service needs, model output or priority scores. A batch containing only unavailable/unverified dossiers is marked failed and retains earlier successful rankings.

## AI provider fallback

Set `AI_FREELLM_FALLBACK_ENABLED=true` to explicitly enable failover from the complete `AI_*` configuration to the separate `FREELLMAPI_*` configuration. It is disabled by default. Each provider receives only its own key. Operational failures (including quotas, timeouts and unavailable models) attempt the fallback; invalid user input does not. The primary is retried after a two-minute cooldown. If the fallback also reports exhausted quota, it has its own two-minute cooldown. This does not bypass either provider's limits. A healthy primary never calls the fallback.

FreeLLM defaults to JSON compatibility mode (`FREELLMAPI_USE_TOOLS=false`), because an advertised capability does not prove that the currently available upstream can serve it. The model receives the JSON schema in its instructions; the same schema, company citation, and service-fit validation still applies. Set this flag true only after verifying native tools with the selected provider. Advertised but rejected tool requests can retry once as plain JSON; quota failures do not trigger that retry. Optional `FREELLMAPI_REASONING_EFFORT` uses FreeLLM's native `reasoning_effort` field independently from OpenRouter. Long encoded feed URLs and hashes stay in stored dossiers but do not consume model context. Candidate extraction and company analysis have separate bounded output budgets.

Responses retain the actual model name, and connection-test responses indicate `provider` and `fallbackUsed`. Local Desktop FreeLLM at `127.0.0.1:31415` works only for the local backend. Hosted preflight rejects loopback fallback addresses; a hosted fallback needs a reachable HTTPS service and its own hosting configuration. No Desktop router is exposed publicly by this change.

## Local operation

Start the backend preview and frontend as before. Saving settings starts the worker, and Research now starts an immediate asynchronous job. The UI polls status; closing the page does not cancel a job. Backend process availability is required. No automatic email or external outreach is sent.

## Hosted scheduling activation

An always-running backend or dedicated cloud worker is required for reliable autonomous operation. The existing sleeping free web service alone cannot promise scheduled execution. A worker can run `node backend/dist/scripts/prospecting-worker.js` with the same cloud database and AI environment settings. Alternatively configure an external scheduler to POST `/api/v1/prospecting/wake` repeatedly with the backend-only `PROSPECTING_WAKE_SECRET` as a Bearer token. Each call processes one step, so wake frequently (e.g. every minute), not merely at the research interval. Keep the secret out of frontend variables and logs. Exact timing depends on source/provider availability and wake frequency. This local change creates no cloud worker, billing commitment, secret or deployment.

The API remains unauthenticated as requested; deployment still needs access control and AI usage protection before broad public use. Wake authorization is restricted separately to prevent arbitrary scheduler calls. Never treat mere presence of a wake secret as proof an external scheduler has been provisioned.
